# N = 112: what the bin count is doing, what bounds it, and what to write instead

Team T5. Scripts: `experiments/n_band.py`, `experiments/n_recommendation.py`,
`experiments/seed_ball.py`. Tables: `data/n_band.csv`, `data/n_recommendation.csv`.

## 1. Where N enters

`N` is the number of bins per phase coordinate in the seed cover (§2.2). With `w = 1/N`:

* **(2.6)** bins `I_b = [b/N, (b+1)/N]`, midpoints `u_b = (b+1/2)/N`, `0 ≤ b < N`;
* **(2.7)–(2.8)** the orientation and midpoint-gap filters, whose thresholds move with `1/N`;
* **Prop 2.10** the fresh-midpoint radius `√9/(2N) = 3/(2N)`, which is what makes a *bin* a ball;
* **Lemma 2.9 / `testBucket`** the reuse test, whose comparison radius is `NR = 3.584` and whose
  threshold is `(fl(.032·112))² − 1e-4 = 12.844956`;
* **§7.3** the tuple counts `C(N+4,5)`, `C(N+3,4)` and the integer types the enumeration uses.

Everything else in the proof — `R`, the `U(2)` grid, the three `(τ,w)` pairs, all nine caps — is
independent of `N`. So the question "why 112" is exactly the question "which of the five entries
above constrains it, and what does moving it cost".

## 2. The constraints, all four of them

| # | statement | inequality | bound on N | source |
|---|---|---|---|---|
| C1 | the tuple counter is a signed 32-bit integer | `C(N+4,5) < 2^31` | `N ≤ 189` | §7.3 |
| C2 | a fresh midpoint covers its own bin with radius `≤ R` | `3/(2N) ≤ .032` | `N ≥ 47` | §2.4 |
| C3 | bin differences are stored in `int8_t` | `N − 1 ≤ 127` | `N ≤ 128` | §7.3 |
| C4 | the coordinatewise reuse bound (2.18) certifies a nonzero integer offset only when `(NR)² > ‖k‖² + 9/4 + Σ|k_j|` | `(NR)² > 4.25` (the minimum over nonzero `k ∈ Z⁹`) | `N ≥ 65` (soft) | §2.4, (2.18) |

Reproduced exactly: `C(116,5) = 160,389,488`, `C(115,4) = 6,913,340`,
`C(193,5) = 2,118,000,528 < 2^31 = 2,147,483,648`, `C(194,5) = 2,174,032,288 > 2^31`.
`3/(2·46) = .032609 > .032` and `3/(2·47) = .031915 ≤ .032`.

**C3 is the constraint nobody has used.** §7.3 says: *"All bin differences lie between −111 and
111 … The stored five-coordinate differences also fit the signed eight-bit type used by the
cover."* At `N = 112` the largest difference is `N − 1 = 111`, which fits `int8_t` with 16 units
to spare; at `N = 129` it is 128, which does not. So the paper's own memory model gives
`N ≤ 128`, and the 32-bit argument quoted as the reason for 112 is the *weaker* of the two by 61
units.

**C4 is soft** — the dual bound (2.19) can succeed where (2.18) cannot — but it is the constraint
that explains why the choice is not at the bottom of the window. The coordinatewise bound's
budget is `(NR)²`; a nonzero offset needs more than `1 + 9/4 + 1 = 4.25` of it, so below `N = 65`
no nonzero integer offset can pass and the reuse test degenerates to "is this the same midpoint as
one already retained". At `N = 64` the budget is `4.194`; at `N = 65` it is `4.326`.

So the honest statement is:

> **N ∈ [47, 128] is admissible and the proof is verbatim correct on all of it.** Inside it,
> `N ≥ 65` is needed for the coordinatewise reuse test to be able to fire, and `N ≤ 128` comes
> from `int8` storage. 112 is a cost choice inside `[65,128]`, at 87.5% of the `int8` ceiling.

That is a strictly better sentence than the one in the paper, because it is falsifiable and it
tells the reader which way to move if they change the machine.

## 3. The cost curve

Exact combinatorics (`n_band.py`): `C(N+4,5) ~ N^5/120`.

| 47 | 2,349,060 | 0.0146 | 230,300 | 1,344,880 | 0.997 | 1.504 | 2.26 |
| 56 | 5,461,512 | 0.0341 | 455,126 | 3,068,142 | 0.837 | 1.792 | 3.21 |
| 64 | 10,424,128 | 0.0650 | 766,480 | 5,781,072 | 0.732 | 2.048 | 4.19 |
| 80 | 30,872,016 | 0.1925 | 1,837,620 | 16,802,948 | 0.586 | 2.560 | 6.55 |
| 96 | 75,287,520 | 0.4694 | 3,764,376 | 40,447,736 | 0.488 | 3.072 | 9.44 |
| **112** | **160,389,488** | **1** | **6,913,340** | **85,349,292** | **0.419** | **3.584** | **12.85** |
| 128 | 309,319,296 | 1.929 | 11,716,640 | 163,401,888 | 0.366 | 4.096 | 16.78 |
| 160 | 929,632,032 | 5.796 | 28,342,440 | 485,985,096 | 0.293 | 5.120 | 26.21 |
| 189 | 2,118,000,528 | 13.21 | 54,870,480 | 1,100,009,104 | 0.248 | 6.048 | 36.58 |

Two things to note.

* `N^5/120` is the right law to quote, but it *understates* the growth between successive
  realistic choices: 96→112 is ×2.13 and 112→128 is ×1.93, i.e. one grid step of 16 costs a
  factor 2, because the binomial is only locally `~N^5/120`.
* `T1(N)`, the number of bin tuples surviving the integral orientation filter (2.7), is the
  quantity the traversal actually touches. It is 53.2% of `C(N+4,5)` at `N = 112` and the ratio
  falls slowly (55.5% at 64, 52.8% at 128), so it does not change the shape of the curve.

## 4. The retained-centre count: what is knowable

`results/plan.md` asks T5 to deliver "retained centre count vs N — the quantity that actually
matters". It cannot be measured here: the authors' code is not in the packet, and re-running the
real cover at five values of N is exactly the computation the paper reports once. What *can* be
said is sharper than a guess, because of one geometric fact:

> The set that must be covered is the same for every `N`, and every ball has radius `R = .032`.
> So the number of centres *needed* does not depend on `N`. Only the efficiency with which the
> greedy reuse test finds them does.

Three consequences, all of them usable:

1. **Upper bound, `N`-independent.** The recorded run produced a cover with 249,878 centres. The
   same set of centres is a legal output at any `N`, so 249,878 centres *suffice* for every `N` in
   the window. A-stage cost is therefore bounded above by `2020.32 s` at every `N` — if the greedy
   were as effective as it was at 112.
2. **Upper bound, `N`-dependent.** At `N` the algorithm cannot retain more centres than there are
   surviving tuples, `T1(N)` (each survivor yields at most one fresh midpoint per bin pair). So
   `centres(N) ≤ min(249,878-efficient bound, T1(N))`, and at `N = 47` that is `1,344,880`,
   i.e. **at most 5.4× the recorded A stage** (`≤ 3.0 h` at the measured 8.09 ms per centre).
3. **Where the risk is.** `(NR)²` is the budget the coordinatewise bound has to work with, and a
   nonzero offset needs more than `4.25` of it: `2.26` at `N=47`, `3.21` at 56, `4.19` at 64,
   `12.85` at 112. So the *reuse efficiency* is a steep function of `N` near the bottom of the
   window and flat near 112. The measured 641.9 bins per retained centre at `N = 112` is what
   buys the 34-minute A stage; at `N = 56` the mechanism is switched off for every nonzero offset
   and the A stage could cost up to 6.9 h, i.e. 10× the whole recorded run.

**Cost table** (`data/n_recommendation.csv`), A stage in hours with the honest uncertainty band:

| N | tuples | cover (s, ×tuples) | A best (h) | A bound (h) | total worst (h) |
|---|---|---|---|---|---|
| 47 | 2,349,060 | 9.1 | 0.56 | 3.02 | 3.0 |
| 64 | 10,424,128 | 40.4 | 0.56 | 13.0 | 13.0 |
| 96 | 75,287,520 | 291.8 | 0.56 | 90.84 | 90.9 |
| **112** | **160,389,488** | **621.6** | **0.56** | **191.69** | **191.9** |
| 128 | 309,319,296 | 1198.8 | 0.56 | 366.98 | 367.3 |
| 160 | 929,632,032 | 3602.8 | 0.56 | 1091.47 | 1092.5 |

The recorded `N = 112` run sits at `0.56 h` (A) `+ 621.6 s` (cover) `= 34 min + 10 min`, inside
a band that is 340× wide. The band is uselessly wide because it mixes "reuse works perfectly"
with "reuse never works"; the recorded run is evidence that at `N = 112` it works (641.9 bins per
centre), and `(NR)² − 9/4 = 10.60` is evidence about *why*.

**The decisive experiment** is cheap and the paper should report it: run the cover and A stage at
`N ∈ {64, 96, 112, 128}` and print (centres, cover seconds, A seconds). Extrapolating from the
table, that is `40 s + A` to `20 min + A` per point, four points, one table. It converts every
number above into a measurement and settles whether a smaller `N` is available. T8 can promise
the table without having it; T5 cannot produce it without the authors' code.

## 5. What breaks if N is halved to 56 or doubled to 224

**N = 56 (half).** *Nothing in the proof breaks.* `3/(2·56) = .026786 ≤ .032` (ratio 0.837), so
Prop 2.10 holds verbatim; `C(60,5) = 5,461,512`, so the cover would take ~21 s instead of 622 s.
What breaks is the *budget*: `(NR)² = 3.211 < 4.25`, so the coordinatewise bound cannot certify
any nonzero integer offset and reuse collapses to exact-duplicate bins. The A stage then carries
the whole run, at up to `T1(56) × 8.09 ms = 6.9 h`, ten times the recorded total. `int8` headroom
is untouched (72 units spare). Also: `N = 56` is only 9 above the hard floor 47, where the
fresh-centre radius uses 99.7% of `R` and nothing at all is left for the `.0320001` enlargement or
for the numeric margins — so 56 is the smallest value a user should ever consider, and it is
where the argument stops being comfortable.

**N = 224 (double).** `C(228,5) = 4,912,679,520`, which is 30.6× the recorded tuple count and
**2.29× the signed 32-bit limit** — C1 fails outright, and the tuple counters of §7.3 would have
to be 64-bit. Bin differences reach 223, so C3 (`int8` storage) also fails: the sentence "the
stored five-coordinate differences also fit the signed eight-bit type" becomes false. The squared
sum `9·223² = 447,561` still fits `int32`, so only the counter and the difference type break. The
cover scales to ~5.3 h and reuse becomes easier (`NR = 7.17`, more than 10⁷ reachable offsets), so
the centre count would fall — but then the 2,000,000-Root and 2,000,000-record caps are exercised
for the first time. Note carefully: **none of these is a proof obligation.** 224 does not break
the mathematics; it breaks the paper's stated memory model. That is precisely why the honest
ceiling is 128 and not 189.

## 6. Recommendation

**Do not change the value; change the reason.** Concretely, replace the paragraph at the start of
§7.3 and the sentence in §2.2 with the following, which states a window, an inequality per end,
and the cost choice. Numbers are from the tables above.

> For the seed cover we take `N = 112`, `w = 1/N`. The choice is constrained at both ends and is
> not otherwise special. *Lower end.* A retained bin midpoint covers its whole bin, because the
> bin is a cube of side `1/N` in nine coordinates and `√9/(2N) = 3/(2N) ≤ .032 = R` holds exactly
> when `N ≥ 47`; at `N = 47` the fresh-centre radius is `.031915`, and at `N = 112` it is `.013393`,
> i.e. 42% of `R`, so the bin ball is never the binding scale for `R`. *Upper end.* The
> five-coordinate bin differences are stored in `int8_t`, so `N − 1 ≤ 127`, i.e. `N ≤ 128`; the
> tuple counter `C(N+4,5)` is a signed 32-bit integer, which would allow `N ≤ 189`
> (`C(193,5) = 2,118,000,528`), so the 32-bit limit alone is 61 units weaker than the storage
> limit and does not determine the choice. *Middle.* The reuse test of §2.4 can certify a previous
> centre at integer offset `k` only when `‖k‖² + 9/4 + 2k·h` falls below `(NR)²`; with
> `NR = 3.584` the admissible offsets are those of norm at most `3.58`, of which there are
> `284,055`, and the recorded run retained one centre per 642 bins. At `N = 56` the same budget is
> `3.21`, below the `4.25` a nonzero offset needs, so the reuse mechanism is effectively switched off; this
> is the reason the value is not simply taken as small as possible. The cost of the choice is the
> enumeration `C(N+4,5) ≈ N⁵/120`, which is `75,287,520` at `N = 96`, `160,389,488` at `N = 112`
> and `309,319,296` at `N = 128`, so moving one grid step of 16 costs about a factor two. We take
> `N = 112` as a cost choice near the top of the admissible band with 16 units of `int8` headroom;
> any value in `[65, 128]` would leave the argument of §2 unchanged.

Then add one sentence to §7.5, next to Table 1: *"The value `N = 112` enters the execution only
through the tuple counts and the `int8` bin differences; a run at any `N ∈ [65,128]` would
establish the same statement with a different cost."*

## 7. What is still open (for T9 and the lead)

**What Table 1's "pairs processed" counts.** Table 1 reports `151,744,086` pairs for the seed
cover. The number of bin tuples satisfying the integral orientation filter (2.7) is
`85,349,292` — computed two independent ways and checked against brute force for `N = 3..9`
(`n_band.py` §6), and independently reproduced by another member's script
(`experiments/n_window.py` prints the same value). `151,744,086` is 94.63% of `C(116,5)` whereas
(2.7) removes 46.79%, so it is **not** the X-tuple filter count; it is not `C(116,5)`, not
`C(115,5) = 153,476,148`, and not `112·C(115,4)`.

The consistent reading is that it counts *bin pairs* — `(X list, Y tail)` combinations offered to
`testBucket` — and not X tuples at all. Two things support it: the paper's own word "pairs", and
the fact that the recorded run then retains `249,878` of them, a reuse factor of `607.3`, which
is the right order for a greedy merge on a five-dimensional set (it is also the number that makes
the all-bins design of `experiments/deterministic_cover.py` cost 14 days instead of 34 minutes).
On that reading `22,829` X lists survive `sumok` out of `85,349,292`, and `151,744,086/22,829 =
6,646.9` Y tails are tried per surviving X list — an average, so nothing out of range.

What should be settled is one sentence of definition and one pair of counts: *is `P` the number of
pairs offered to the reuse test, and how many of them pass each filter?* Without that, the only
recorded number that pins the traversal cannot be checked, and the completeness claim of
Prop 2.10 — which is about *that* traversal — rests on an unexplained total. **This is the one
place where a wrong number in `results/` mattered and was caught**: the reading "151,744,086 is
the (2.7)-filter count" is wrong by a factor 1.78 and would have been published.

**`q_d`, the retained-bin count, the cluster count and the `mid.bin` radii are all unreported.**
They are not needed for the cost argument above, but they are what would turn §4's bounds into a
measurement.
