# K2-2 — four traps that are not about `centers.txt`

Team K, member m2, direction k2. Continuation of `K2-1.md`. These bite rungs R2 and R6 through
artefacts other than the centres file. Logs: `work/10-recreate/crew/m2/`.

## H-7 (blocker) — the recorded stdout cannot be produced by the published sources, and the shipped checker enforces the recorded format

Every driver's `printf` in the published sources differs from the recorded capture in
`execution/results/*.txt`, and the shipped checker `fullmatch`es the recorded form, so the
published format is rejected:

| what | published source | recorded `results/…` | checker regex |
|---|---|---|---|
| covrun header | `xs%zu build%.2f` (`covout.cpp:139`) | `xs 22829` | `check_records.py:240` `xs [1-9][0-9]*` |
| covrun progress | ` t%d/%zu cells%lu centers%zu` (`:130`) | absent (3 lines total) | `:240` `len(cover_lines)==3` |
| covrun N-line | `…centers%zu visit%lu near%lu cheap%lu lp%lu` (`:132`) | `…centers249878` | `:242` fullmatch ends at `centers(\d+)` |
| covrun tail | `time %.2f` (`:142`) | `completed_write` | — (no source line prints it) |
| arun | `done %d G%zu failedBalls%lu coverFailures%lu+%lu` (`atlas.cpp:233`), `total done%d candidates%lu patches%lu global%zu failedBalls%lu time %.2f` (`:237`) | `done 1000 G181 failedBalls0`, `total done62470 global764 failedBalls0` | `:260`, `:268` |
| brun | `done%zu/%zu ->%zu bad%zu time %.1f ` (`stageB.cpp:324`) | `done50/600 ->20213 bad0 parent50 …` | `:165`, `:177` |
| crun | `done%lu bad%zu (…) avg bins%.0f balls%.0f time %.1f` (`stageC.cpp:553`) | `done100 bad0 (graph0 cap0 over0 cluster0)` | `:198` |

Two of the five covrun differences (`xs 22829`, `completed_write`) cannot be produced by any
filter of the published output, so the recorded run's `covout.cpp` was not the published file.
The rest are consistent with either a filter or an older printf — either way the checker is
format-exact.

**Settling test.** `bash work/10-recreate/crew/m2/checkerdemo/checkerfmt.sh` (log `RESULT.txt`,
23.6 s). It copies `results/`, symlinks `data/`, and substitutes each driver's published format.
Recorded verbatim: `PASS within numerical consistency scope`. Every published-format
substitution: `NOT ESTABLISHED`, with the specific complaint (`cover seed completion is absent
or malformed`, `cover terminal center count differs`, `unexpected A progress line`, `unexpected
C result line`, `unexpected B progress line`).

**Consequence.** Plan §5 R6 ("the shipped checker and ours both pass on our output") is
unsatisfiable for a build that prints what the published sources print. And a faithful build
cannot satisfy it by "fixing" the printfs: those are the object of the recreation. The
criterion must be restated.

**Guard (V).** (i) run the shipped checker on the *recorded* tree — it passes in 2.7 s
(`cd crew/m3/saved-run/execution && python3 check_records.py .`), which is a check of the record,
not of us; (ii) run our own checker on our output; (iii) compare only the data channel
(`commands.json` `outputs`) byte-for-byte; (iv) if our stdout is compared at all, compare parsed
numbers, not bytes — `checked151744086` and `centers249878` are recorded and deterministic, and
are a free independent witness for R2.

## H-8 (major) — the empty-bad-file criteria cannot distinguish "correct" from "absent"

Four `bad0..3.txt` are 0 bytes and four `fb1cbad0..3.bin` are 8 bytes (`uint64` 0) in the record
(verified). The natural shell test, `[ ! -s "$f" ] && echo empty:PASS`, is **also true when the
file does not exist**, so a `crun` that never ran satisfies the R6 final-pass criterion. These
eight files are the only ones where "the program ran and wrote nothing" must be distinguished
from "the program did not run", and both obvious tests conflate them.

**Settling test.** `test ! -s /nonexistent && echo pass` prints `pass`.

**Guard (V).** for `bad*.txt`: `test -f && stat -c %s == 0`; for `fb1cbad*.bin`:
`test -f && stat -c %s == 8 && test "$(od -An -tu8 -N8 "$f")" -eq 0`; both plus mtime ≥ run
start.

## H-9 (minor) — the probe does not test `pow(x,2)`, and both cover-square sites compile to libm calls

`VERIFY.md` makes an explicit precondition for using a fresh `covrun` as evidence: "inspect the
two `pow(..., 2)` expressions in `coverSeeds::run` … Merely finding no dynamic `pow` symbol is
insufficient." `build.sh:28` writes the disassembly and nothing checks it. In the known-good
upstream binary both sites are calls: `.scratch/gh/build/covrun.disassembly.txt` offsets
`0x53fa` and `0x543f` call `pow@plt`, inside `coverSeeds::run` (the `nm -D` listing does carry
`U pow@GLIBC_2.29`, so the "no dynamic symbol" shortcut would not even be available).

On this host the calls are numerically inert, but only because of two particular arguments:
`crew/m2/probes/rn2.cpp` shows `pow(3.584,2) == 3.584*3.584` and
`pow(sqrt(RN2)+1.5,2) == (…)*(…)` bit for bit (`RN2 = 0x1.9b09e12a51e33p+3`, `T = 0x1.9d8cf5d94ea5ap+4`,
`int T = 25`). `crew/m2/probes/pow2.cpp` shows why that is luck and not a theorem:
`pow(x,2) != x*x` for **1765 of 3 998 080** random binary64 inputs on this glibc 2.43 —
1 ulp, e.g. `x = -0x1.569c58474ed03p+125`.

`abi-fp-probe.cpp:44-48` tests only `sqrt(2)`; there is no `pow` test anywhere in the probe.

**Consequence for the harness.** R2 passing does not establish the arithmetic contract the paper
assumes at the two sites its own `VERIFY.md` names — the pass depends on an untested libm
property, and on a host with a differently rounded `pow` the same sources would fail R2 for a
reason that has nothing to do with our re-derivation. That failure mode is invisible in advance.

**Guard (V).** R0 adds (i) a runtime assertion `pow(x,2) == x*x` for the two actual arguments
(scale and second square of the cover square), and (ii) the sample test of `pow2.cpp`; R2's log
records both plus `grep -c 'call.*<pow' ` on the `coverSeeds::run` range of the disassembly, with
a note in the log when it is 2 rather than 0.

## H-10 (minor) — three build-tree hazards

1. `.scratch/gh/upstream/build.sh` **cannot build**: `build.sh:4` cds to `$(dirname $0)/source`,
   which does not exist in that cache (the eight `.cpp` files are flat there). Verified: rc 1,
   `cd: …/upstream/source: No such file or directory`. Only `.scratch/gh/cb/` (and the fetched
   `compiled-build/`) has `source/`.
2. `build.sh:8-11` exits 2 on an existing output directory (verified). A wrapper that writes
   `bash build.sh "$DIR" || true` then runs a stale binary from `$DIR` — see H-1.
3. `fetch_saved_run.py:45-47` derives `REPO_ROOT` as `HERE/../../..` and defaults the cache to
   `work/10-recreate/crew/m3/saved-run`: the code depends on its own location, and the R2
   reference lives in another member's private scratch. Copying the script elsewhere silently
   redirects the cache (measured: `--check` then reports 308 missing — fail-closed, but the
   error looks like cache corruption).

**Guard (V).** name the buildable tree explicitly (the fetched `compiled-build/`, never a glob
for `build.sh`); `set -e` around the build; `--cache` mandatory in `verify.sh`, pointing at a
V-owned directory created by the wave.
