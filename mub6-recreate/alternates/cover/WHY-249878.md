# Why exactly 249 878 centres result

Short answer: 249 878 is the cardinality of one deterministic greedy maximal cover, not a
value predicted by a formula. What can be established, and is established here, is the
exact accounting by which that number arises, which parts of it are forced by the
mathematics, and which are choices of the specification.

## 1. The count is a function of the seed set alone
`coverSeeds::run` has no RNG, no clock, no threads and no unordered container. Its input
is the pair of seed families (`xs`, 22 829 cells; `ys`, 829 306 cells) and its iteration
order is fixed: `t` ascending over `xs`, and inside `t` the list `Y[A.p.b[A.p.s]]` in
stored order. Every accepted cell is appended to `all` immediately, so `all` is ordered by
`(t, position in ys)` and the file inherits that order (spec §5.2). Two runs therefore
agree bit for bit, and the fixture shows the seed set itself is reproduced bit for bit.

## 2. The exact accounting (integers, verified against the published counters)
Every candidate B for every A falls into exactly one of three branches:

```
Sum_{A in xs} |ys[A.b[A.s]]|                      = 298 638 554     (candidate pairs)
  dropped by the gap filter        (covout.cpp:122) = 108 445 934
  dropped by the interval filter   (covout.cpp:123) =  38 448 534
  checked                                           = 151 744 086
```
and every checked pair is either certified covered or accepted:

```
checked                              = 151 744 086
  covered by the cheap L2 test       =  45 648 766
  covered by the LP dual certificate = 105 845 442
  accepted (the file)                =     249 878
```
The last identity uses my extra counter `lpok`, whose value is forced by the published
`checked`, `cheap` and `centers`. Over all 3.13 billion LP attempts the certificate
succeeds 105.8 million times (3.4%).

## 3. The three filters, and which of them are mathematics
- **Gap filter** (`B.p.g + 1e-8 < 1-(A.b[4]+2)w`): a canonicalising condition. It admits
  only pairs whose two bin clusters lie in one span, i.e. one representative per
  rotational class. It is *not* a feasibility test: switching it off multiplies the count
  by 5.2 (F4.2). The figure 249 878 is only defined with it on.
- **Interval filter** (`B.hi < A.lo || B.lo > A.hi`): a genuine feasibility test — the
  pair must admit a common shift of the shared coordinate. Switching it off adds 99
  centres on the prefix (F4.3), which is 0.2% of the retained cells: the interval test is
  sharp enough to reject essentially everything that is geometrically impossible.
- **Covering test**: a pair is discarded when an *earlier accepted* centre within the
  squared bin distance `RN2 = (R n)² - 1e-4 = 12.844956` certifies it. Soundness needs
  the certificate to be an upper bound on the achievable squared distance; the cheap test
  `s+a+2.25 < RN2` is the L2 bound, the LP test `s+2.25+supdual < RN2` is a two-step
  weighted-least-squares dual bound with per-bin phase error `1.251 π w`. The `2.25` is
  the squared cell radius `(3/2)²`; `T = (sqrt(RN2)+1.5)²` is the prefilter that follows
  from it. Under-covering is harmless (it only leaves work for later stages);
  over-covering would be unsound.

## 4. Why the bucket structure cannot change the answer
A candidate can survive the test only if the sum of the four squared free-bin differences
is at most `int(T) = 25`, hence each `|k_i| ≤ 5`. The `covered()` window reaches ±5 for
`K=3` (exactly) and ±7 for `K=4`; both cover every possible candidate, so both give the
same centre list. Measured: identical bytes at `K=3,m=38` and `K=4,m=28` (F4.1), only the
`visit`/`near` counters differ. The library's constants are 4 and 28 (F1).

## 5. What is *not* claimed
No closed form, no "minimal cover", and no robustness in the certificate strength:
tightening the LP to `dual=6` changes the count (F4.5) and its centre set is not a subset
of the `dual=2` set (F6), because the greedy procedure is not monotone in the covering
relation. So the honest statement is: 249 878 is reproduced exactly, its accounting is
integer-exact and auditable, and the only parameter variation that provably cannot change
it is the bucket layout.
